## 1. 概要

### 1.1 アプリ概要

ローカル音楽ファイルを対象に、曲の指定区間のみを再生しながら次々と曲を切り替えていく音楽プレイヤーアプリ。

### 1.2 コンセプト

> 忘れていた曲に、次々と出会い直す体験

- 短時間で多くの楽曲を再生する
- 懐かしい曲・埋もれた曲を再発見する
- 作業用BGM・流し聴き用途にも使える

### 1.3 コア価値

- 時短で多くの曲を聴ける
- 懐かしい曲との再会
- 流れを止めない再生体験

## 2. ターゲットユーザー

- ローカルに大量の音楽を保存しているユーザー
- 昔の楽曲をよく聴いていたユーザー
- フル再生ではなく部分的に楽しみたいユーザー

**Android（決定：2026-09-02）**

  ライブラリが内部で`NSPhotoLibraryUsageDescription`のAPIを参照するため、

  OS権限APIかを意識せず共通コードで動く。両OSとも権限拒否時の復旧フロー

## 4. コア機能

### 4.1 再生機能

- ローカル音楽ファイルの再生
- 再生 / 停止 / 次の曲 / 前の曲
- シャッフル再生
- リピート再生（OFF → 全曲リピート → 1曲リピート の3状態。普通のプレイヤー準拠）

### 4.2 区間再生機能（メイン機能）

**パラメータ**

- 再生開始位置（秒）
- 再生時間（秒）

**指定方式**（決定：2026-09-02、％対応は2026-09-11に不要と判断し撤回）

- 秒指定（絶対値）のみに対応する
- 曲の長さに対する相対指定（％）は当初「秒とセットで両対応」の方針だったが、使う場面が薄いと判断しスコープから外した
- 秒指定が曲の長さを超える場合の扱いは「境界処理」（下記）で解決済み

**設定スコープ**（決定：2026-09-02）

- 区間設定はキュー全体で共通の**全体設定**を使用する
- プレイヤー画面のスライダー操作は、常に**全体設定の変更**として扱う（曲ごとの個別設定を暗黙に作らない）

**曲ごとの個別設定（却下：2026-09-11）**

- 曲ごとに区間設定を上書きする機能は実装しないと決定した。全体設定のみを使う

**動作**

- 指定した区間のみを再生し、終了後に次の曲へ遷移する

**境界処理**（決定：2026-09-02）

- 開始位置＋再生時間が曲の長さを超える場合：超過分は再生せず、**曲の終端でフェードアウトして次の曲へ**遷移する
- 開始位置が曲の長さを超える場合：**0秒（曲の先頭）から**再生する

### 4.3 RUSHモード（自動スキップ）

本アプリの中心となる再生モード。

UI上の表示名は「メドレー」（メドレー ON / OFF、**2026-09-11 決定**）。「RUSH」は
初見で機能が伝わらないという判断による変更。UI表示名は `Skip` → `RUSH` →
「メドレー」の順で2度変わっており、古いスクリーンショットやメモに `Skip` の
表記が残っていてもこの変遷を辿れる。コード内の変数名・関数名や、本書での呼称は
引き続き RUSH のまま（検索性のため書き換えない）。

**RUSH ON（デフォルト）**

- 区間再生を有効にし、区間終了時にフェードアウトして次の曲へ自動遷移する

**RUSH OFF**

- 区間再生を無効にし、通常の音楽プレイヤーとして曲を**最初からフル再生**する
- 開始位置へのシークも行わない
- 曲が最後まで再生されたら次の曲へ遷移する

**再生中に ON/OFF を切り替えた場合**（決定：2026-09-02）

- 切り替えは**次の曲から適用**する（シャッフルボタンと同じ感覚）
- 区間設定（Start / Length）の変更も同様に次の曲から反映する
- 再生中の曲を区間の開始位置へシークし直すことはしない
- ただし **OFF にした場合のみ**、再生中の曲の区間カットも即座に解除し、そのまま最後まで再生する（シークはしない）

### 4.4 フェード（必須）

**フェードアウト**

- 区間の終了直前に音量を徐々に下げる
- フェード時間：1〜5秒（デフォルト2秒）

**フェードイン**（決定：2026-09-03）

- 区間の開始直後に音量を徐々に上げる（デフォルト1秒）
- ネイティブ側で音量を制御しているため実装コストが小さく、追加した

**クランプ**

- 実効フェード時間 = `min(設定値, Length ÷ 2)`
- イン・アウトそれぞれに適用するため、両者が重なることはない
- 例：Length=3秒 / Fade=5秒 → 実効フェード 1.5秒

**クロスフェードは実装しない**（決定：2026-09-03）

- 曲を重ねる真のクロスフェードは対象外とする。曲は重ならない（疑似クロスフェード）
- Media3 に組み込みAPIが無い（androidx/media#2 が2021年から未解決）。実装するには
  ExoPlayer 2台構成と、それを1つの論理プレイヤーとして MediaSession に見せる層が必要
- 実測で曲間の無音が平均約50msに収まっており、現在の方式で十分滑らかと判断した

## 5. キュー管理

### 5.1 キュー生成モード（排他）

- 全曲
- アーティスト（複数選択可）
- アルバム（複数選択可）

生成の導線はライブラリ画面の選択モードに統合する（→ 10.3）。

### 5.2 キュー生成ルール

- 選択条件に一致する楽曲をすべて追加する
- 同一楽曲の重複は排除する

### 5.3 再生終了時の挙動・リピート（2026-09-08 実装）

リピートは3状態で、押すたびに **OFF → 全曲 → 1曲 → OFF** の順に巡る
（一般的なプレイヤー準拠）。プレイヤー画面とウィジェットの両方に置く。

| 状態 | キューの最後まで再生したとき |
|---|---|
| OFF | 停止する |
| 全曲 | 先頭へ戻る。1巡の完了として扱い、次の巡を作る（6.2） |
| 1曲 | 同じ曲を繰り返す。1巡の進捗は動かない |

設定はネイティブ側のプレイヤーが持ち、QueueStore に控える。アプリを終了しても、
ウィジェットから起こしたときも前回の設定で始まる。既定は全曲。

JS 側はキューを積むときにリピートを上書きしない。上書きすると、利用者が選んだ
設定が再生のたびに戻ってしまう。

## 6. シャッフル再生

「シャッフルにしても同じ曲ばかり流れ、大半の曲が一生再生されない」問題の解消を目的とする。
RUSHモードとは**独立した機能**であり、RUSH ON / OFF のどちらでも同じように動作する。

### 6.1 基本仕様（普通のプレイヤー準拠）

- キュー内の曲から**順列を1つ生成**して順に再生する（再生ごとに独立抽選する方式は採らない）
- 1巡内で同一曲の重複なし
- シャッフルON/OFFの切り替えは**次の曲から適用**する（再生中の曲はそのまま継続）
- シャッフルON中の「前の曲」は**再生履歴を遡る**（元の並び順の前の曲ではない）
- シャッフルOFF時の並び順は、再生元となった一覧の表示順に従う（例：楽曲タブなら曲名順）

### 6.2 1巡状態の永続化（本アプリの肝）

UI上は「1巡」の概念自体を出さず、プレイヤー画面ヘッダーには**キュー内の位置**
（`status.index + 1` / `queue.length`）だけを表示する（**2026-09-11 決定**）。
シャッフルキューでは `RetracksPlayer.setQueue(ordered, state.cursor, key)` で
ネイティブのキューに順列全体が入り `state.cursor` から再生が始まるため、
`status.index + 1 === progress.played`・`queue.length === progress.total` が
常に成り立つ。「1巡」という語も「シャッフル」という語も不要で、`playFrom`
（曲を順番に再生）由来のキューでも同じ式でそのまま位置が出せる（それまでは
シャッフルキューのときだけ数字が出たり消えたりしていた）。「1巡」は本書・
コード内（`reconcile()`・`isCycleComplete()`等）の呼称としては引き続き使う。
デバッグ画面（14章・状態カード）は「1巡」表示のまま据え置いている。永続化
されたシャッフル状態のカーソルという別概念を見せている場所であり、UI上の
「1巡」の唯一の出口として残す判断（RUSH→メドレーと同じ型）。

- 生成した順列と現在位置（カーソル）を、**アプリ再起動をまたいで保存**する
- 起動時は保存済みの順列とカーソルを復元し、続きから再生する
- 1巡し切るまで、既に再生した曲は再び選ばれない
- これにより「毎回シャッフルし直して順列の先頭付近だけを聴く」状態を防ぐ

**保存単位**

- キューの生成条件ごとに順列を保持する（全曲 / アーティスト選択 / アルバム選択 /
  曲を選んだシャッフル）。順番に再生も、並びと位置を保存する（アーティスト／アルバム
  詳細で曲をタップして再生した、その途中までも残す）。**保存しないのは、曲タブを
  複数選択なしでタップした再生と、検索結果のタップ**（その場で選んで聴く使い方で、
  項目が増えて途中経過を押し出すため。2026-10-15 追加。→ 10.4「キュータブ」）
- 別のキューを再生してから戻っても、元のキューの順列と位置は失われない
  （※これにより旧「シャッフル状態の保持」仕様は自動的に満たされる）
- 保存の上限：全曲は、上限であふれても残す（1巡の進捗が押し出されないように。利用者が
  ゴミ箱で消したときだけ消える。→ 10.4）。それ以外は、
  シャッフル系を最後に再生を始めた順に20件、順番再生を10件まで（あふれた分は
  順列・カーソル・位置・メタデータごと捨てる）
- 以前は「曲を選んだキュー（`selection:`）は同じ組み合わせを選び直さないので保存しない」
  としていたが、キュータブから続きを再生できるようになったため、保存する（キーは
  選んだ曲IDのハッシュ）

**ライブラリが変化したとき**

- 削除された曲：順列から取り除く
- 追加された曲：順列の**未消化部分にランダムに挿入**する（新しく入れた曲がすぐ出てくるように）

**1巡し終わったとき**

- リピートON：順列を作り直して2巡目に入る
  - カーソルを0に戻す実装とコストが変わらないため、多様性が出る「作り直し」を採用する
  - 2巡目の先頭が1巡目の末尾と同じ曲になった場合は引き直す（同じ曲が2回続くのを防ぐ）
- リピートOFF：停止する

### 6.3 進捗の可視化

- プレイヤー画面ヘッダーにキュー内の位置（例：`109/982`）を表示する
  （**2026-09-11 決定**：UI上は「1巡」の概念を出さない → 6.2）。
  シャッフルキューでは結果的に1巡の進捗と同じ数字になるため、
  「ライブラリをちゃんと一周できている」ことは変わらず可視化される
- デバッグ画面では従来どおり1巡の進捗として表示する（6.2）

## 7. 再生制御仕様

### 7.1 再生開始

- 曲開始時、指定した開始位置へシークする

### 7.2 スキップ判定

- 再生位置ベースで区間終了を判定する

### 7.3 フェード処理

- 区間終了直前でフェードアウトを開始する
- フェード終了と同時に次の曲の再生を開始する

### 7.4 読めない曲の扱い（2026-09-07 決定）

他のアプリで曲が削除されても、キューにはその曲が残る。走査は都度おこなわないため、
キューを作った時点のファイルが今もあるとは限らない。

- 読み込みに失敗した曲は**黙って次へ送る**。停止しない
- 送ったあと prepare をやり直し、元の再生状態（再生中／一時停止）に戻す
- リピートが有効だと次の項目は必ず存在するため、キューを一周しても
  1曲も鳴らせなければそこで停止する

キューから消しはしない。順番と1巡の進捗は JS 側が持っており、ネイティブ側で
項目を抜くと番号がずれるため。消えた曲が一覧から消えるのは次の走査時。

### 7.4.1 区間の付け外しはメディアソースを作り直す（2026-09-08 実測）

区間は MediaItem の ClippingConfiguration に焼き込むため、RUSH を切り替えたら
次の曲以降を組み直す必要がある。このとき **replaceMediaItems を使ってはならない**。

Media3 は曲が同じならメディアソースを作り直さず、MediaItem の参照だけ差し替える。
区間なしのソース（ProgressiveMediaSource）は差分判定で ClippingConfiguration を
見ないため、区間を**付ける**変更が黙って捨てられる。外す方は区間ありのソースが
比較するので効く。この非対称のせいで「RUSH の ON だけ効かない」という形で出た。

`removeMediaItems` + `addMediaItems` に置き換えてソースごと作り直させる。

組み直す範囲は**いま鳴っている曲以外のすべて**。後ろだけにすると、切り替えた
あとに前へ戻ったとき、そこは切り替え前の状態が残る（RUSH を切ったのに数曲は
短縮のまま鳴る）。前側を消すと現在位置の添字がずれるので、**後ろ側を先に**
処理する。いま鳴っている曲だけは組み直さない（頭から鳴り直すため）。

紛らわしいのは、`getMediaItemAt(i).clippingConfiguration` は**新しい値を返す**点。
設定は入っているのに再生は変わらないので、値を読むだけの確認では見抜けない。
実際に鳴らして曲の長さを見ること。

### 7.5 再生中のセッションの引き継ぎ（2026-09-07 決定）

アプリのプロセスだけが落ちて再生が続いている場合や、ウィジェットから再生を
始めた場合、JS はあとから起動して鳴っているセッションに合流する。

- **キューはネイティブ側から貰う**。JS の保存を当てにして番号だけを
  当てはめてはならない
- 1巡の進捗は、保存してある順列が鳴っているキューと**完全に同じ並び**の
  ときだけ引き継ぐ。長さの一致だけでは判定しない
- どのキューを鳴らしているかの識別子もネイティブ側に控える

これを守らないと、全曲シャッフルの順列に別キューの番号を当てはめてしまい、
画面と音が食い違う（2026-09-07 に実際に発生）。

## 8. バックグラウンド機能

- バックグラウンド再生に対応する
- 画面ロック中も再生を継続する
- スリープ中も再生を維持する

### メモリと再生の安定性（2026-09-06 実測）

外出時に再生が突然止まる症状を調査した結果を記録する。

**原因はメモリではなくクラッシュだった。**

  ForegroundServiceDidNotStartInTimeException
    at RetracksWidgetProvider.onReceive

ウィジェットから `startForegroundService` でサービスを起こしたあと、期限内に
`startForeground` を呼んでいなかった。修正済み（→ PlaybackService.onStartCommand）。

**再生中のプロセスは保護されている**

  oom_score_adj = 200 / Proc #1 / fg-service
  画面OFFで4分経過しても再生継続

上限は 1001（空きプロセス）。前面のUI（0）に次ぐ位置で、メモリ不足で終了させられる
可能性は低い。終了履歴に残っていた LOW_MEMORY はいずれも `state=empty` のプロセスに
対するもので、再生が終わったあとの通常の回収だった。

**Pulsar との比較**

同じ端末の同じ時点で `dumpsys meminfo -d` を取った。

| | Pulsar | RE:TR4CKS |
|---|---|---|
| TOTAL PSS | 325.9MB | 228.7MB |
| Graphics | 211.0MB | 0.06MB |
| Native Heap | 73.9MB | 1.9MB |
| Bitmap | 490枚 / 43.0MB | 286枚 / 27.6MB |
| **SWAP PSS** | **2.0MB** | **131.7MB** |

**この数字から「RE:TR4CKS の方が軽い」とは言えない。** 測定時の状態が揃っておらず、
RE:TR4CKS 側は背景に回ってメモリの多くが退避された状態だった（SWAP PSS 131.7MB）。
一方 Pulsar は退避がほとんど無い。

言えるのは「**RE:TR4CKS が Pulsar より明らかに重いという結果は出ていない**」まで。

参考として、RE:TR4CKS の別の時点の値：
- 前面で一覧を大量にスクロールした直後：PSS 326MB
- 再生中・画面OFF・4分経過：PSS 362MB（Native 141MB / Graphics 84MB / Bitmap 482枚 59MB）

測定条件によって 229〜362MB の幅がある。常時 362MB を占有し続けるアプリではない。

なおビットマップは1枚あたり約122KB（およそ174×174相当）で、デコード時の縮小は
正しく効いている。残るのは枚数であり、表示に必要なぶんに近い。

**効果があった対処 / なかった対処**

- 効果あり：一覧の描画範囲を絞る（getItemLayout、windowSize）。PSS 543→326MB、
  Graphics 118→25MB
- 効果あり：背景での画像キャッシュ破棄。ビットマップ 790→633枚
- 効果なし：背景で一覧の画像描画をやめる。撤去済み
- 効果なし：expo-image 導入そのもの（単体では 277→543MB と悪化。描画範囲の
  調整と併せて初めて下がった）

**方針**：メモリ削減それ自体を目的にした最適化はしない。行うのは、LMK のリスクや
再生の安定性に対する根拠を示せる場合に限る。再現性のあるメモリ起因の不具合が
出るまでは追加の最適化を行わない。

**この記録を書くにあたっての注意**：当初、Pulsar の測定値と RE:TR4CKS の別時点の
測定値を並べて「同等」と結論づけていた。比較として成立していなかったため訂正した。
測定値を比較する際は、取得した時点とアプリの状態が揃っているかを必ず確認すること。

### 既知の制約：通知をスワイプで消した場合（2026-09-03 実測）

通知をスワイプで消すと、再生は続くが通知は戻らない。曲送りや一時停止など
**再生状態が変わったタイミングで自然に復活する**。

アプリ側から復活させる方法を検証したが、いずれも効果が無かった。

- 通知はスワイプ後もシステム上は posted のまま残る（`activeNotifications` に残存）
- そのため同じ内容を再投稿しても再表示されない
- `cancel` してからの再投稿、`stopForeground` を挟んでの再投稿も効果なし

ユーザーが明示的に消した通知をアプリ側から復活させられないのは、Android 14 以降の
方針に沿った挙動と考えられる。無理に押し通すとフォアグラウンドサービスの状態を
崩し、バックグラウンド再生（本章の必須要件）を損なうリスクの方が大きいため、
プラットフォームの挙動として受け入れる。

### 既知の不具合：ウィジェットから起こしたときに通知が出ない（2026-09-09 実機で発覚・修正済み）

**症状**：アプリを一度も開いていない状態でウィジェットから再生すると、再生自体は
問題なく始まるが、通知にもロック画面にも何も出ない。ロック画面には（再生していない）
Pulsar のメディアカードが代わりに表示される。アプリを一度開いてから再生すると
正しく出る。

**原因は2つ重なっていた。**

1. **`POST_NOTIFICATIONS` 権限を一度もリクエストしていなかった**
   Android 13（API 33）以降、この権限が無いと `NotificationManager` への投稿は
   フォアグラウンドサービス用も含めてすべて黙って握りつぶされる（サービス自体は
   問題なく前面で動き続けるため気づきにくい）。マニフェストにも無く、実行時
   リクエストのコードもどこにも無かった。`dumpsys package` の runtime permissions
   一覧に `POST_NOTIFICATIONS` 自体が存在しないことで発覚した。

   対処：マニフェストに `<uses-permission>` を追加し、`RetracksPlayerModule` に
   `requestNotificationPermissionAsync()` を生やして起動時にリクエストする
   （`src/playback.tsx` の起動シーケンスに追加。結果は問わずライブラリ読み込みは
   続行する）。

2. **`MediaSession.Builder.build()` はセッションを Media3 の通知管理に登録しない**
   権限を直しても直らなかった。`dumpsys notification` で実際に投稿されている
   通知を調べると、`channel=retracks_playback`（自前の仮通知）のまま
   `actions` も `category` も付かない状態で固定されており、Media3 本来の
   通知（`channel=default_channel_id`, `category=transport`, `vis=PUBLIC`）に
   一度も差し替わっていなかった。

   `MediaSession$Builder.build()` を `javap -c` で逆アセンブルして確認したところ、
   中身は `new MediaSession(...)` を返すだけで、サービス側の通知管理
   （`MediaNotificationManager`）には一切触れていない。普段「勝手に登録される」
   ように見えていたのは、JS 側の `MediaController.Builder(...).buildAsync()` が
   接続する際に `onGetSession()` 経由で暗黙に登録されていたため。ウィジェットから
   `startForegroundService` で起こした経路は、サービス内で `player.play()` を
   直接呼ぶだけでコントローラが一切つながらないため、この暗黙の登録が起きない。
   セッションは存在し `active=true` で `MediaButtonReceiver` にも正しく載るのに、
   通知管理の対象としては認識されないという食い違いだった。

   対処：`PlaybackService.onCreate()` でセッションを作った直後に
   `addSession(mediaSession)` を明示的に呼ぶ。あわせて
   `setShowNotificationForIdlePlayer(SHOW_NOTIFICATION_FOR_IDLE_PLAYER_ALWAYS)`
   （既定だと曲が止まっている・未再生の間は通知を出し渋る）と、
   `onStartCommand()` で `player.play()` の直後に `triggerNotificationUpdate()`
   を呼び、仮通知から本物の通知への差し替えを明示的に急がせている。

**調査の要点（再発時のために）**：`dumpsys media_session` でセッションが
`active=true` で最上位にあることを確認しても、それは「セッションが存在し正しく
機能している」ことの証明にしかならず、「通知がちゃんと出る」こととは別問題。
実際に投稿されている通知の中身（`dumpsys notification` の `channel=` /
`actions=` / `category=` / `vis=`）を、正常に動いている他アプリ（今回は Pulsar）
と見比べて初めて「仮通知のまま固定されている」ことが分かった。

### ホーム画面ウィジェット

**Android**：`RetracksWidgetProvider.kt`（→ 13.3）。アートワーク・曲名・
アーティスト名に加え、リピート・前の曲・再生/一時停止・次の曲・「この曲を
最初から」の5操作を持つ。`PlaybackService`のイベントで即座に更新され、

  グラウンドで生きている間だけ確実に動く」という、Androidと異なる制約が

実装は公式`expo-widgets`パッケージ（`expo: ~57.0.19`と同一バージョン、

同じ曲では書き込みをスキップし、Android版ウィジェットの教訓
「切り替わるたびにデコードし直すとネイティブメモリを消費する」→ 13.5
を踏まえた設計）。Android向けには同名の空実装（`src/widgetSync.ts`）を
置き、`src/playback.tsx`の`onTrackChange`ハンドラからOSを問わず同じ
関数を呼べるようにしている。

### 10.3 キュー作成（ライブラリ画面の選択モード）

**概要**：専用画面は設けず、ライブラリ画面上の**長押し → 複数選択**でキューを作る。
アーティストやアルバムをまとめて選んで「簡易プレイリスト」として流す使い方を主眼に置く。

**導線**

1. アーティスト / アルバム / 楽曲タブで項目を**長押し**すると選択モードに入る
2. 以降はタップで複数選択できる（選択数をヘッダーに表示）
3. アクションを選ぶ
   - **再生**：選択対象の楽曲でキューを生成し、プレイヤー画面へ遷移して再生を開始する
   - **削除**：選択対象を端末から削除する（Android 10 以降のみ。→ 10.3.1）
   - **プレイリストとして保存**：ユーザー作成プレイリストに保存する（Phase 2）

```
┌──────────────────────┐
│ ✕  3件選択     ▶  ⋮ │  ← 選択数 / 再生 / その他
├──────────────────────┤
│ ☑ Artist A     22曲  │
│ ☑ Artist B     16曲  │
│ ☐ Artist C      4曲  │
│ ☑ Artist D      8曲  │
└──────────────────────┘
```

**仕様**

- 選択条件に一致する楽曲でキューを生成する（同一楽曲の重複は排除 → 5.2）
- 複数選択は同一タブ内で行う
- 「全曲」キューは選択モードを使わず、楽曲タブのシャッフルFABから生成する
- キュー生成後はプレイヤー画面へ自動遷移し、再生を開始する（決定：2026-09-02）

### 10.3.1 端末からの削除（2026-10 決定、Android 10 以降のみ）

**対応プラットフォーム**：Android 10 (API 29) 以降のみ。削除ボタン自体を
表示しない範囲は次のとおり（判定は `src/useDeleteTracks.ts` の
`CAN_DELETE_TRACKS`）。

- **iOS**：ミュージックライブラリ（MPMediaLibrary）から曲を削除する公開 API を
  Apple が提供していないため、技術的に不可能
- **Android 9 (API 28) 以前**：`ContentResolver.delete()` に
  `WRITE_EXTERNAL_STORAGE` の実行時許可が要る。ところが `expo-music-library` が
  実行時に要求するのは `READ_EXTERNAL_STORAGE` だけ（`ExpoMusicLibraryModule.kt`
  の `getManifestPermissions()`）で、target 26 以上では同一権限グループの
  暗黙の付与もされない（Android 8.0 の変更）ため、許可が取れず
  `SecurityException` になる可能性が高い。実機を持たず検証できない権限要求
  コードを足すより非対応と割り切った（決定：2026-10。依頼時の「Android 11以降に
  対応できればよい、10はできれば」という範囲にも沿う。実機・エミュレータでの
  確認は未実施で、上記は仕様とソースからの判断）

**ストア掲載文・リリースノートで触れるときの注意**：対応範囲は Android 10 以降のみ
（Android 9 以前と iOS では削除ボタンが出ない）。掲載文（`docs/google-play-listing.md`・
`docs/ios-app-store-listing.md`）やリリースノートでこの機能に触れる場合は、「Android 10
以降」と明記し、iOS 版の文面には入れない（2026-10-15 時点では、どちらの文書にも
削除機能への言及は無い）。

**導線**：選択モード（→ 10.3）のヘッダーに、曲・アルバム・アーティストいずれの
選択でもゴミ箱アイコンを出す。アーティスト／アルバムを選んだ場合は、その
収録曲すべてが削除対象になる。確認ダイアログ（「選択した{{count}}曲を端末から
削除します。この操作は元に戻せません」）を経てから実行する。

**Android バージョンによる挙動の違い**（`modules/retracks-player/android/.../RetracksPlayerModule.kt`
の `deleteTracksAsync()`）

| バージョン | 方式 | 確認ダイアログ |
|---|---|---|
| 11 (API 30) 以降 | `MediaStore.createDeleteRequest()` | 選択曲**まとめて1回** |
| 10 (API 29) | `RecoverableSecurityException` を1件ずつ処理 | **曲数ぶん**（OS側の制約。実装の簡略化ではない） |
| 9 (API 28) 以前 | 非対応（ネイティブは reject、JS は削除ボタンを出さない） | — |

- URI は JS から渡さず、ネイティブ側で `Track.id`（MediaStore の行ID）から
  `content://` を組み立てる。`expo-music-library` は API 28 以下で
  `Track.uri` に `file://` を返す（`AssetUtils.kt`）ため、URI を渡す契約に
  すると API 差が JS に漏れる。現状は API 29 以降のみ対応で差は表に出ないが、
  この契約を URI 渡しに戻さないこと
- 戻り値は実際に削除できた件数。ユーザーが確認ダイアログを拒否した場合は
  エラーではなく、その時点までに削除できた件数（0 を含む）を返す。0件なら
  選択状態を保持しやり直せるようにし、1件以上なら選択解除＋再走査する
- `reject` するのは、削除フロー自体が成立しなかった場合（Activity が取得
  できない・確認ダイアログを表示できない・id が不正・API 28 以下）と、
  Android 10 で全件が `delete()` の例外で失敗した場合。JS はこれを
  「削除できませんでした」のアラートにする。失敗を黙って0件扱いにすると、
  ユーザーが拒否したときと見分けがつかず、ボタンを押しても何も起きない
  ように見える（2026-10、レビュー指摘）
- Android 10 (API 29) の曲数ぶんダイアログは、**1件でも拒否した時点で
  打ち切る**（残りの曲の確認ダイアログは出さない）。「この1曲はやめる」では
  なく「この操作全体をやめる」という意思表示として扱う。継続扱いにすると、
  拒否するたびに次の曲のダイアログが出てしまい、50曲のアルバムなら最大50回
  拒否しないと終われない（2026-10、レビュー指摘）
- 削除フローの共通処理（確認ダイアログ・ネイティブ呼び出し・再走査の要否判断）は
  `src/useDeleteTracks.ts` に集約。選択からの絞り込みは `src/library.ts` の
  `tracksForSelection()` に集約し、曲タブ／アルバム詳細／アーティスト詳細の
  3画面で共有する（別々に書くと「再生」と「削除」の対象がズレる事故がある
  ため）

**再生キューとの関係**：削除してもネイティブの再生キュー・JS の `queue`・
永続キュー（QueueStore）からは**取り除かない**（7.4「読めない曲の扱い」と同じ
方針）。再生中の曲を削除した場合、ファイルディスクリプタを開いたままの間は
鳴り続けることがあるが、次にそのファイルを開き直すタイミング（曲の再生成・
シーク等）で読み込みに失敗し、7.4 の `skipUnplayableListener` が黙って
次の曲へ送る。削除直後に強制停止・キューから除去する対応は意図的に行わない
（決定：2026-10。限定的な事象であり、再生系の複雑化に見合わないと判断）。

**既知の制約（未対応のまま残した項目）**

- Android 10 では `delete()` をメインスレッドで1件ずつ同期的に呼ぶ。通常は
  1件ごとにユーザー確認のダイアログが挟まるため密なループにはならないが、
  確認が要らない曲が大量に並ぶと理論上は引っかかり・ANR の恐れがある（実測
  していない）。Android 11以降はシステム側が処理するため影響なし
- Android 10 の経路は実機・エミュレータで未検証（Pixel 11 は Android 17 のため
  Android 11+ の経路のみ確認済み）
- アルバム・アーティスト詳細で全曲を削除すると自動的に前の画面へ戻るが
  （空の詳細画面を残さないため）、ライブラリ画面のタブ自体が空になった
  場合の遷移は特に設けていない（タブの「端末内に音楽がありません」表示に任せる）

### 10.4 ライブラリ画面

**概要**：端末内の楽曲をタブで切り替えて閲覧・再生する。Pulsar の構成をベースとする。

```
┌──────────────────────┐
│ ≡  RE:TR4CKS   🔍  ⋮ │
├──────────────────────┤
│ アーティスト│楽曲│PL  │  ← タブ
├──────────────────────┤
│                      │
│  （タブごとの一覧）   │
│                      │
│                 (⤮)  │  ← シャッフル再生FAB
├──────────────────────┤
│ 🎵 曲名        [⏸][⏭]│  ← ミニプレイヤー
└──────────────────────┘
```

**タブ構成**

| タブ | 内容 |
|---|---|
| アーティスト | アートワーク付きグリッド。アーティスト名 / アルバム数 / 曲数を表示 |
| アルバム | アートワーク付きグリッド。アルバム名 / アーティスト名 / 曲数を表示 |
| 楽曲 | 全曲のリスト。曲名 / アーティスト名 / 再生時間を表示 |
| 続きから | 再生を始めたキュー（全曲・アーティスト・アルバム・選んだ曲・順番再生）を新しい順に並べ、タップで続きから再生する（2026-10-15 実装。内部IDは`queues`。下の「キュータブ」） |
| プレイリスト | 自動プレイリスト（最も再生された＝再生回数 / 最近の追加曲）＋ ユーザー作成プレイリスト（お気に入りは端末をまたいで持ち運べないため対象外に決定。「最近再生された」は要否保留 → 15章16番） |

**仕様**

- タブは設定で**並び替え・表示非表示**を変更できる（→ 10.7）
  - タブ候補：アルバム / アーティスト / フォルダ / ジャンル / 楽曲 / プレイリスト
- 項目を**長押し**すると選択モードに入り、複数選択からキューを作成できる（→ 10.3）
- 一覧から曲をタップすると、**その一覧をキューとして**再生を開始する（普通のプレイヤー準拠）
  - RUSH ON なら区間再生、RUSH OFF ならフル再生（→ 4.3）
- シャッフル再生用のFABを配置する
- 検索機能を持つ

**キュータブ（ラベルは「続きから」）**（2026-10-15 実装、`feat/queue-tab`）

アプリが記憶している再生の続き（6.2）を一覧にして、そこから再開できるようにする。
上の「プレイリスト」（自動／ユーザー作成。未実装）とは別物なので、`TabId` は
`queues`とし、`playlists`にしない。ラベルは「続きから」/ "Resume"（当初は「キュー」としたが、
プレイヤー画面の「再生キュー N曲」（いま鳴っている並び）と同じ語で別の意味になるため変えた。
**内部IDの`queues`は変えない**：`normalizeTabs()`が未知のIDを捨てるので、リリース後に変えると
利用者が設定したこのタブの並び順・表示設定が黙って初期化される。ラベルだけなら`library.tabQueues`を直す）。

- 並べるもの：全曲、アーティスト（複数選択可）、アルバム（複数選択可）、曲を選んだ
  シャッフル、順番再生（複数選択の「順番に」、アルバム／アーティスト詳細の「順番に」ボタン）。
  アーティスト／アルバム詳細の曲タップも含む。新しい順。保存の規則は 6.2。
  **曲タブを複数選択なしでタップした再生と、検索結果のタップは並べない**（一覧や検索結果を見ながら
  その場で選んで聴く使い方で、タップや検索語のたびに項目が増え、アーティスト／アルバムの途中経過を
  押し出すうえ、続きから再生する価値が無い）
- 1行の表示：見出し（複数選択したものは、**選んだものを全部「 / 」で連ねる**。「クリープハイプ / Sezko / Number_i」
  のように。区切りは文言（`queues.nameSeparator`、日英とも前後にスペースを含む「 / 」）で、1か所で変えられる。曲を選んだキューは、同じアルバムの曲でも選んだ曲名を連ねる。1行に収まらない分は行の末尾を
  省略する。全曲は「全曲」。名前が無い旧データは「先頭の曲名 ほか N件」）、
  サブタイトル（種類 · 途中の曲名）、右端に `N/M`、ジャケットは途中の曲のもの
- タップ：続きから再生してプレイヤー画面へ。**鳴っているキューは積み直さず**
  プレイヤー画面を開くだけ（積み直すと最大5秒前の保存位置まで戻る）。鳴っている
  キューはオレンジで強調する
- 削除：行右端のゴミ箱（確認あり。「このキューだけが消えます。曲は端末から削除されません。」
  消えるのは一覧の項目と、その再生位置の記録だけで、曲は消えない）。「再生リスト」という語は、
  未実装のプレイリスト〔下の表〕と紛らわしく、タブ名・確認のタイトル（「キューを削除しますか？」）とも
  呼び名が分かれるので使わない。
  **鳴っているキューには出さない**（鳴っているキューを消すと、曲が変わるたびにカーソルが
  書かれて、一覧に載らない保存内容が残る）。全曲にも出す（確認の文言が違い、1巡の進捗が
  消えて、次に全曲シャッフルを押すと新しい順列で最初から始まる。画面下のボタンの
  「全曲シャッフル再開 N/M」も元に戻る）
- **全曲は、いつ使ったかに関わらず、一覧の1番上に固定する**（保存の上限で押し出されない
  ことが、並びからも分かる）。残りは、最後に再生を始めた順
- 曲がライブラリに1つも見つからないキューは薄く表示し、タップすると
  「続きから再生できません」を出す（削除はできる）
- タブは設定の並び替え・表示/非表示の対象（既存ユーザーには既定で末尾に表示される。
  `normalizeTabs()`が足す）。選択モード・並べ替え・表示形式の切り替えは持たない

**保存の形**（`src/queueKeys.ts`・`src/queueStore.ts`）

| キー | 内容 |
|---|---|
| `all` | 全曲シャッフル（従来どおり） |
| `artist:<ID,ID,…>` / `album:<ID,ID,…>` | アーティスト／アルバムのシャッフル（従来どおり。IDは並べ替えて連結） |
| `songs:<hash>-<件数>` | 曲を選んだシャッフル（旧`selection:`）。選んだIDのハッシュ。同じ組み合わせは同じキューとして続きから再生する |
| `seq:<hash>-<件数>` | 順番再生（複数選択の「順番に」など、一度きりの用途）。曲IDの並びのハッシュなので、同じ並びは同じキューになる |
| `seq:artist:<hash>` / `seq:album:<hash>` | アーティスト／アルバムの詳細（と、1件だけ選んだ「順番に」）からの順番再生。出所のIDのハッシュ（アルバムは、開いた経路で`id`が違う〔プレイヤー画面はアルバム名、ほかはalbumId〕ので、曲から`albumId || album`で求めたIDにそろえる。`albumOriginId()`）。詳細画面の並べ替えを変えても、曲が増減しても、同じ出所は1項目のままで、別の曲をタップするとその項目の並びと位置を上書きする（並びのハッシュだと、そのたびに同じアーティストの項目が増え、10件の枠から別のアーティストの途中経過が押し出される） |

- **キーを分解して意味を取り出さない**。MediaStore がIDを持たない曲は名前がIDの代わりに
  入るため、`artist:`以降をカンマで割れない。何のキューかは、再生を始めるときに
  メタデータ（選んだID・表示名のスナップショット）として別に保存する。
  この機能の前に保存された旧データはメタデータが無いので、いまのライブラリに実在する
  IDだけで組み立て直せたときに限って拾い、続きから再生するときに保存し直す
- 順番再生の並びは `shuffle` とは**別の名前空間**（`ordered:v1:`）に保存する。同じ
  場所に入れると、起動時の復元（7.5）が「シャッフル中」と誤判定し、リピート全曲で
  1巡して先頭へ戻るたびに順列を作り直してしまう
- 順番再生の並びは保存時点のスナップショットで、曲は足さない（シャッフルの`reconcile()`
  とは違う）。続きから再生するときに、ライブラリから消えた曲だけ詰める
  （途中だった曲が消えていたら、その次の曲を頭から）
- 1曲だけの順番再生は保存しない（続きに価値が無く、一覧を埋めるだけ）
- **再生位置の保存先**：曲が変わったとき・5秒ごとの保存は、シャッフル状態があるか、保存中の
  順番再生のときだけ書く。どちらでもないキュー（1曲だけの順番再生・旧版が作った識別子の
  無いキュー）はキーが`all`のままなので、書くと全曲の位置を別のキューの位置で
  上書きする（v2.48）
- **続きから再生する手順**：保存位置は、キューを切り替える**前に**読む（`setQueue()`が
  出す`onTrackChange`のハンドラが位置を0に書き戻すため）。シークは`setQueue()`の直後ではなく、
  読み込みが済んでから（`seekWhenLoaded()`。1247曲のキューでは直後のシークが無視される）。
  どちらも v2.48

**実機で確認した範囲**（Pixel 11、Android 17、debugビルド＋Metro、2026-10-15）：
旧データ（メタデータ無しのアーティスト／アルバム）の表示と続きから再生、複数アルバム選択の
シャッフル（選んだ順の名前・`album:ID,ID`のキー）、曲を選んだシャッフル（`songs:`のキー。
`selection:`のキーが残らない）、順番再生（`seq:`。曲タップでの保存をやめる前の確認で、保存・更新・削除は確認済み）、続きから再生（1247曲の
全曲キューと`seq:`で位置まで戻る）、`playFrom`後も`position:all`が変わらないこと、削除
（保存内容・一覧・メタデータが全部消える）、アプリを終了して起動し直してもキュータブが復元され、
鳴っていた順番再生がオレンジ表示になること。**未確認**：iOS（Simulatorには音楽ライブラリが
無く再生できない。iOS向けバンドルが生成できることだけ確認）、ライブラリから曲が消えた後の
続きから再生（ロジックは単体で確認、実機では未）、4タブの幅が狭い端末での見え方。

**並べ替え（曲・アルバムタブ、アーティスト詳細の曲一覧）**（2026-09-11 決定）

曲タブ・アルバムタブ・アーティスト詳細の曲一覧は、ヘッダーの並べ替えアイコンから
軸と方向（昇順/降順）を選べる（メニュー方式。いずれも方向を持つため巡回式の
ボタンにはできない。モーダル自体は `src/components/SortMenu.tsx` として共通化）。

| 画面 | 軸 | 既定 |
|---|---|---|
| 曲タブ | タイトル / アルバム名 / アーティスト名 / 長さ | タイトル昇順 |
| アルバムタブ | アルバム名 / アーティスト名 / 発売年 | アルバム名昇順 |
| アーティスト詳細の曲一覧 | タイトル / アルバム名 / 長さ / 発売年 | **発売年降順** |

- プロバイダの `tracks`/`albums`（タイトル順の正本）は変更しない。各画面が
  表示用に並べ替えた配列を別に持つ（→ `src/sortOrder.ts`）。SettingsProvider に
  持たせると、その値の変更で `PlaybackProvider` の `tracks` が再計算され、
  `artists`/`albums` の導出やライブラリ全体の絞り込みまで連鎖して走り直すため、
  意図的に分離した
- 第2・第3キーは `compareByTrackOrder()`（ディスク・トラック番号順）を流用する。
  「アルバム順」「アーティスト順」「発売年順」で同じアルバム内の曲が散らばらない
  ようにする（アルバム順→アルバム名→ディスク→トラック番号、アーティスト順・
  発売年順→アルバム名→ディスク→トラック番号）。方向（昇順/降順）は主軸にだけ
  効かせ、第2・第3キーは常に自然な順のまま（降順にしたときアルバム内の曲順まで
  逆転すると使い物にならないため）
- アルバムの発売年（`Album.year`。アーティスト詳細では曲が属するアルバムの
  発売年）が無いものは、方向に関わらず常に末尾に寄せる
- 選んだ軸・方向は端末に保存し、次回も同じ状態で開く（→ `StorageKeys.sortOrder`）。
  アーティスト詳細は曲タブとは別のキー（`artistTracks`）で持つ（既定が
  発売年降順で、曲タブのタイトル昇順とは異なるため）
- 「順番に再生」は画面に表示している並び順をそのまま使う（複数選択時も同様）
- アーティスト詳細の曲一覧は、既定を**発売年降順**にする（2026-09-12）。
  ディスコグラフィとして新しい作品から辿りやすくし、同じ発売年の中では
  アルバム名→ディスク→トラック番号の自然な順を保つ
- 設定画面の「先頭の The / A・An を無視」は並べ替えの**規則**（同じ軸の中での
  比較方法）であり、ここでいう並べ替えの**軸**とは別物。混同を避けるため設定画面の
  見出しを「並べ替えの規則」に変更した（→ 10.6）

**対象外（v1）・フェーズ2として記録**

- ライブラリ画面のアーティストタブ：軸が「名前」の1つしか無く、並べ替えメニューを
  置く意味が無いため対象外。「アルバムアーティスト」軸を足せば意味が出るが、
  expo-music-library が ALBUM_ARTIST を扱っておらず自前のネイティブクエリが要る
  （`getTrackFolders()` と同じ方式）ため、フェーズ2で改めて検討する
- アルバム詳細の曲一覧：ディスク/トラック番号順が前提のため対象外
- アーティスト詳細の**アルバム一覧**（上部のグリッド）：発売年降順で固定。
  ディスコグラフィは新しい順が見やすく、並べ替えの対象は曲一覧のみとした
- 「追加日」軸：Track に持っていない（`Asset.creationTime` は走査時に取得できるが
  保存していない）。足すならキャッシュ版を5→6に上げる作業が伴うため見送った
  （曲タブ・アーティスト詳細とも）

### 10.6 設定画面

Pulsar を参考にした構成。MVPで必須のものと、あれば嬉しいものを分けて考える。

**優先度：高**

- タブ項目の変更（表示するタブの選択と並び替え）（**実装済み・2026-09-10**）
  - 曲・アーティスト・アルバムの3タブを対象に、表示/非表示と並び順を設定できる
  - 最低1タブは表示必須（保存データの破損時は `normalizeTabs()` が全既定へ
    戻す。設定画面側も最後の1枚はスイッチを disabled にして操作自体を防ぐ）
  - 副作用として、全曲シャッフルの導線（FAB）を曲タブの中からライブラリ
    画面レベルへ移した。元々は曲タブの中にしかなく、アーティスト/アルバム
    タブでは出ていなかった（タブを隠せるようになる以上、消えると困る導線を
    タブの内側に置いたままにはできないため）
  - 検索結果のセクション見出しは、タブの表示設定から独立させた
    （`search.sectionSongs/Artists/Albums`）。タブを隠すことは「そのデータを
    扱わない」ことを意味しないため（検索や曲からアーティスト/アルバムの
    詳細画面へは、タブを隠していても到達できる）
- 音楽以外のファイルを除外する（着信音・通知音・アラーム・オーディオブックなど）
  （**実装済み・2026-09-10**）
  - **発見（2026-09-10）**：`expo-music-library` は MediaStore の `IS_MUSIC` を
    一切見ていない（ネイティブ実装の `ASSET_PROJECTION` にも `createSelection()`
    にも登場しない）。着信音・通知音・アラーム・オーディオブック・ポッドキャストが
    曲一覧に素通しで混ざっていた。恐らくこれが「短い曲を除外」を既定ONにした
    主因（通知音は数百msで短いため）。自前ネイティブモジュールに
    `getTrackFolders()` を追加し、`IS_MUSIC` が明示的に0の曲を除外できるように
    した（NULLは音楽として扱う＝除外しない安全側）。デフォルトON
  - ラベルは「着信音・通知音を除外」ではなく「音楽以外のファイルを除外」にした。
    `IS_MUSIC` はオーディオブック・ポッドキャストにも0が立つため、狭いラベルだと
    原因に辿り着けない利用者が出るため
  - 対象・スコープは「短い曲を除外」と同じ制約（下記）
  - 実機計測では「音楽以外を除外」単体で968曲、「短い曲を除外」単体で971曲、
    両方ONでも968曲（実測1027曲中）。通知音等はほぼ短い曲側とも重複しており、
    「短い曲を除外」の既定ONの主因はこちらで解消される。この計測結果を受けて
    「短い曲を除外」の既定値を見直した（下記）
- 除外するフォルダ（自炊音源などIS_MUSICで拾いきれない残り向け）
  （**実装済み・2026-09-11**）
  - 設計変更（2026-09-10）：フォルダ一覧は `expo-music-library` の
    `getFoldersAsync()` を使わず、`getTrackFolders()`（上記）が返す
    フォルダID/名前とスキャン済み `rawTracks` から組み立てる方針に変更。
    `getFoldersAsync()` 由来だと、Android 10未満のフォルダIDが
    `expo-music-library` 内部のハッシュ実装と一致している前提が必要になる
    （自前で完全再現するのはリスクが高い）ほか、件数がアプリ内の絞り込み後の
    実態と食い違う
  - 除外IDの保存は、タブの `normalizeTabs()` とは逆に「正本と突き合わせて
    未知のIDを捨てる」をしない。SDカード未マウント等で一時的に一覧に出ない
    フォルダのIDを捨てると、除外設定が黙って消えるため
  - UI（2026-09-11）：Pulsarを参考にした専用画面（`app/excluded-folders.tsx`）。
    ＋ボタンでモーダルを開き、チェックボックスで複数選択してOK、一覧の各行は
    タップで個別解除。ただし候補フォルダの取得方法はPulsarと異なる。
    Pulsarはファイルシステムを直接ブラウズしており、それには
    `MANAGE_EXTERNAL_STORAGE`（すべてのファイルへのアクセス）が要るが、
    音楽プレイヤーアプリではGoogle Playの審査で基本的に却下される権限
    （海外展開の前提と相性が悪い）。代わりに MediaStore が認識済みの
    フォルダ（`usePlayback().folders`、曲が入っているフォルダのみ）を候補にした。
    曲の無いフォルダを除外する意味は無いため実用上の支障は無い
- 短い曲を除外する（例：5秒未満）（**実装済み・2026-09-10**）
  - **デフォルトはOFF、しきい値5秒**
    - 2026-09-03：既定OFFで決定
    - 2026-09-10：既定ONへ変更（通知音などの混入が主因と推定）。同日中に
      「音楽以外のファイルを除外」を追加
    - 2026-09-11：「音楽以外のファイルを除外」により既定ONにしていた主因が
      解消されたと判断し、既定OFFへ戻した。
      `IS_MUSIC` は MediaStore 全体の規約で、Ringtones/Notifications/Alarms
      配下には端末を問わず0が立つため、この解消は端末依存ではない。
      一方、既定ONのまま残す副作用は一方向（5秒未満の実在する曲—SE・
      インタールード・隠しトラックなど—を黙って隠す）だった
  - しきい値は5〜120秒の範囲で5秒刻み
  - 対象は曲一覧・検索・全曲再生/シャッフル・曲一覧からの複数選択再生に加えて、
    アーティスト/アルバムのトラック数表示・詳細画面の一覧・そこからの複数選択
    再生にも及ぶ（2026-09-11、下記のアーティスト/アルバム導出の作り替えにより、
    どちらも同じ絞り込み済み `tracks` から作られるようになったため）
- アーティスト/アルバムのID（2026-09-11、上記の導出の作り替えに伴う既知の制約）
  - `deriveArtists()`/`deriveAlbums()`（→ src/library.ts）のグループ化キーは
    `artistId || artist` / `albumId || album`。ID が欠けた曲だけ名前に落ちる
    （Android ではほぼ常に ID が入るためレアケース）が、この名前は
    ルートパラメータ（`/artist/[id]` 等。`/` を含む名前で問題になりうる）と
    `buildQueueKey()` の `ids.sort().join(',')`（`,` を含む名前で問題になりうる）
    の両方に流れ込む。同一アーティストの曲の一部だけ `artistId` が欠けていると
    一覧上は2つのアーティストに割れる、という副作用もある。以前は必ず数値の
    MediaStore ID だったため起きなかった種類の問題
- 一覧の並べ替え順（**実装済み・2026-09-10**）
  - 曲・アーティスト・アルバムのタイトル/名前でクライアント側ソートに統一
  - 先頭の "The " を無視するかを設定できる（既定ON）
  - "A"/"An" も別トグルで無視できる（既定OFF）。Pulsar はまとめて1つの設定

## 13. 技術方針

調査日：2026-09-02

### 13.1 基本構成

| 領域 | 採用 | 備考 |
|---|---|---|
| フレームワーク | Expo (SDK 57) / React Native 0.86 | New Architecture のみ（RN 0.82 で旧アーキ廃止、0.85 で互換層も削除） |
| ビルド | **ローカルビルド**（Android Studio） | Kotlin を書くため反復コンパイルが前提。Expo Go は不可 |
| **再生層** | **自前の Expo モジュール**（Android: Kotlin + Media3／iOS: Swift + `AVPlayer`/`MPMediaLibrary`、2026-09-14追加） | 既製ライブラリでは要件を満たせないため（→ 13.2） |
| ライブラリ走査 | expo-music-library | 曲/アルバム/アーティスト/ジャンル/アートワークを取得 |

### 13.2 再生層を自前で持つ理由

**要件 9.1 / 9.2（通知・イヤホンからの「次の曲」）が既製ライブラリで満たせない。**

Android でこれを実現するには、MediaSession が `COMMAND_SEEK_TO_NEXT_MEDIA_ITEM` を
公開し、かつ処理する必要がある。イヤホンの2タップも `KEYCODE_MEDIA_NEXT` として
この経路を通るため、通知ボタンの有無と同じ問題になる。

| 候補 | 判定 | 根拠 |
|---|---|---|
| expo-audio 57.0.4 | ✗ | `AudioMediaSessionCallback.onConnect` が `COMMAND_SEEK_TO_NEXT_MEDIA_ITEM` 等を明示的に `remove()` している。`AudioPlaylist` は `next()/previous()` を持つが、`AudioControlsService` が `AudioPlayer` 型のみ受け付けるため MediaSession に載らない |
| react-native-track-player V4 (4.1.2) | ✗ | レガシーアーキテクチャ用モジュール。RN 0.85 でブリッジ互換レイヤーが削除済みのため現行 RN では動作しない |
| react-native-track-player V5 (@rntp/player) | △ | 要件は満たすが商用ライセンス €999/年〜 |
| react-native-video | ✗ | 単一メディア前提でキュー概念が無く「次の曲」が成立しない |
| react-native-audio-pro | ✗ | アーカイブ済み |

**自前実装を選ぶ判断根拠**

1. 差別化要素（区間再生・フェード・RUSH・1巡シャッフル）がすべて再生層にある。既製プレイヤーの「曲を頭から最後まで流す」前提と根本的に噛み合わない
2. ~~**Android専用**のため iOS 実装が不要で、コストが概ね半分で済む~~ →
   **前提が変わった（2026-09-14）**：iOS版も追加することになり、この判断根拠は
   成立しなくなった。ただし既製ライブラリで要件を満たせないという1の理由は
   iOSでも同様に当てはまるため、自前実装という結論自体は変わらず、Swift版
   （`RetracksPlayerModule.swift`）を追加する形で対応した（→ 13.3の追記）
3. MediaSessionService を自分で持てば、通知/イヤホン/Android Auto が素直に手に入り、フェードもネイティブ側で滑らかに実装できる

### 13.3 自前モジュールの責務

ローカル Expo モジュール（`modules/` 配下）として実装する。

**モジュール側（Kotlin / Media3）**

- ExoPlayer によるローカルファイル再生
- MediaSessionService（通知・ロック画面・イヤホン・Android Auto）
- **区間の切り出し**：`MediaItem.ClippingConfiguration` で開始・終了を宣言し、ExoPlayer
  自身に切らせる。位置をポーリングして終了を検出する方式は精度が出なかったため採らない（→ 13.4）
- **フェードイン／アウト**：音量ランプ。数百ms のずれは聴感に出ないため、こちらは
  50ms 間隔のループで制御する

**JS側**

- ライブラリ走査（expo-music-library）
- キュー生成・シャッフル順列・1巡状態の永続化（→ 6章）
- UI 全般
- 区間設定の解決（`src/rush.ts`。秒/％の吸収もここ）

**モジュール側（Swift / AVFoundation、2026-09-14追加）**

- `AVPlayer`によるローカルファイル再生、`MPMediaLibrary`（`MPMediaQuery`）で
  ライブラリを走査・アートワークを取得
- MPNowPlayingInfoCenter・MPRemoteCommandCenter（ロック画面・イヤホン操作）
- **区間の切り出しとフェード**：AndroidのClippingConfigurationとは異なり、
  `AVPlayer.addPeriodicTimeObserver`（時刻監視のコールバック）で再生位置を
  監視し、区間の終端で次の曲へ進め、区間の前後で音量を直接操作してフェード
  させる方式（`RetracksPlayerModule.swift`）。Androidで「ポーリング方式は
  精度が出ない」と判断した経緯（上記）とは異なる実装になっているが、iOS実機
  でのフェード精度・区間切り替わりの厳密な計測はまだ未実施
  （`docs/ios-release-checklist.md`の未消化項目）
- JS側の責務はAndroidと共通（`RetracksPlayerModule.ts`のインターフェースを
  両OSで共有し、JS側は呼び出し先の違いを意識しない）

### 13.4 技術検証の結果（2026-09-03 / Pixel 9a / Android 17)

| # | 項目 | 結果 |
|---|---|---|
| 1 | **通知・イヤホンからの「次の曲」** | ✅ **合格**。ロック画面に前/次ボタンが表示され、イヤホンのタップで次・前・再生・停止すべて動作 |
| 2 | 区間再生の精度 | ✅ ClippingConfiguration へ変更し **±25ms**（変更前は 173〜265ms） |
| 3 | フェードの品質 | ✅ 合格。フェードイン／アウトとも滑らか（→ 下記の注意点あり） |
| 4 | 曲の切り替わりの間 | ✅ **32〜66ms（平均約50ms）** |
| 5 | バックグラウンド動作 | ✅ 合格。画面ロック中も再生継続 |
| 6 | ライブラリ走査の速度 | ✅ 合格。**1025曲 / 69アーティスト / 195アルバムを 3983ms** |

**#1 が通ったことで 13.2 の判断（再生層を自前で持つ）が裏付けられた。** 構成は確定とする。

**走査についての知見**

- ライブラリが 1025曲 で 1000件を超えるため、`getAssetsAsync` のページング（上限1000）が必須だった
- 起動のたびに約4秒かかるため、曲一覧はキャッシュする設計が要る。シャッフル順列の
  永続化（→ 6.2）と保存先を揃えて検討する

**再測定（2026-09-10）**：`getTrackFolders()`（IS_MUSIC・フォルダ情報の取得。
ページングと並行に投げる設計）を追加した後、デバッグ画面の「再走査」で
**1027曲 / 916ms**。2026-09-03時点の3983msとは条件が違う（3983msは起動時の
コールドスキャン＝キャッシュ無し・OSのページキャッシュも冷えた状態。916msは
アプリ稼働中の手動再走査＝直前にも MediaStore へ問い合わせている状態）ため、
両者を直接比較してベースラインが縮んだとは言えない。この再測定で確認したいのは
「`getTrackFolders()` 追加による劣化が無いこと」のみで、それは満たしている。

**区間の切り出し方式について**

当初は 50ms 間隔で再生位置を監視して終了を検出していたが、実測のズレが 173〜265ms と
監視間隔の 4〜5倍に達した。原因はメインスレッドが UI 描画で混み、Handler のコールバックが
遅延すること。切り出しを `MediaItem.ClippingConfiguration` に委ねる方式へ変更した。
ExoPlayer がサンプル単位で切って自動的に次へ進むため、ポーリングが判定経路から外れる。
開始位置へのシークも不要になる。

代償として、区間設定を変更した際に MediaItem を組み直す必要がある。ただし再生中の曲まで
差し替えるとその曲が区間の先頭から鳴り直してしまうため、`replaceMediaItems` で
**現在の曲は触らず次の曲以降だけを差し替える**（決定：2026-09-03）。
設定変更は「次の曲から反映」となる。

**フェードの実装で判明したこと（重要）**

`player.volume` は「いま鳴っている音」ではなく、**これから AudioTrack へ書き込むサンプル**に効く。
ExoPlayer は音声を先読みして書き込むため、再生位置を見てそのまま音量を絞ると、実際に
ゲインがかかるのは概ね 250ms 先の音になる。結果として次の症状が出た。

- 前の曲の末尾がフェードされずフル音量のまま鳴る
- 次の曲の冒頭に、前の曲用のフェードアウトのゲインがかかる

**対処**：ゲインの計算に `再生位置 + WRITE_AHEAD_MS(250ms)` を使い、音量の適用先と
位置を合わせた。実機で症状が解消することを確認済み。

**残るリスク**：250ms は実測に基づく経験値で、端末や Android バージョンによって
先読み量が変わる可能性がある。ずれが再発する場合は、PCM サンプルに直接ゲインを掛ける
`AudioProcessor` 方式が根本解になる（音声パイプラインの中でゲインがサンプルと一緒に
流れるため、位置APIの粗さともバッファの先読みとも無関係になる）。ただし ExoPlayer は
ギャップレス再生時に音声シンクをフラッシュしないため、曲の境界をサンプル列の中で
知る仕組み（区間長のFIFOと、シーク時の再同期）を別途作る必要がある。

**位置APIの粗さについて**

`player.currentPosition` は実測で約260ms ごとにしか更新されない。そのまま使うと
フェードが階段状になるため、値が変わらない間は経過時間で補間している。

**実装上ハマった点（再発防止のため記録）**

- `MediaController` はメインスレッドからしか操作できない。Expo Modules の `Function` /
  `AsyncFunction` は JS スレッドで動くため、コントローラに触る処理は明示的に
  メインスレッドへ回す必要がある
- prebuild が生成する構成は `expo-splash-screen` の存在を前提としている
- **再生中にネイティブヒープが増え続け、OSに強制終了される**（2026-09-11、実機で発覚・修正）
  - 症状：再生中、Javaヒープは健全なまま（25MB/256MB）ネイティブヒープだけが
    数分でGB単位まで増え続け、Android（Pixel）の `MemoryLimiter:AnonSwap` に
    強制終了された
  - 原因：`usePlayback()` の Context `value` を毎レンダー作り直していたため、
    再生位置を250ms間隔でポーリングする `setStatus()` のたびに `value` が
    新しい参照になり、React の仕組み上それを使う全画面が再生中ずっと毎秒
    複数回再レンダーされ続けていた。ネイティブヒープが増えるのは、この頻度
    で Fabric のシャドウツリー側の確保が積み上がっていたため
  - 切り分け方（この3点で「レンダー駆動」と確定できた。次に似た症状が
    出たときに使える手順）
    1. バックグラウンドにすると増加が完全に止まる（画面を描画していない
       間は起きない）
    2. 一時停止中（値が1つも変わっていない）でも止まらない
       （＝表示内容ではなく再レンダーの回数そのものが原因）
    3. ポーリング間隔を伸ばすと増加率がほぼ比例して下がる
  - 対処（→ `src/playback.tsx` / `app/player.tsx` / `src/components/MiniPlayer.tsx`）
    - 250msごとに変わる `status` を専用の別 Context（`usePlaybackStatus()`）
      に分離し、`usePlayback()` の残り（tracks/artists/albums/queue/操作関数
      等）は `useMemo` で参照を安定させた。生の再生位置が要る3箇所
      （MiniPlayer・プレイヤー画面・デバッグ画面）だけが毎秒再レンダーされる
    - プレイヤー画面のシークバーとキュー一覧の行は、値が同じでも再レンダー
      されるたびにネイティブ側の処理が走っていたため `React.memo`/
      `useCallback` で安定化した。インラインの `onPress={() => skipTo(index)}`
      のような「行ごと・レンダーごとに新しい関数」を渡すと memo が無効化
      されるので注意（`QueueRow` は `onPress(index)` を受け取る形にして
      親から1つの安定した関数を渡すよう直した）
    - `RetracksPlayer.getStatus()` は中身が同じでも毎回新しいオブジェクトを
      返すため、フィールドを浅く比較して変化が無ければ `setStatus` に前の
      値をそのまま返させ、React に再レンダーを止めさせるようにした
      （`statusEquals()`）
    - ポーリング間隔自体も250ms→1秒に変更（プログレスバーとしては体感上
      問題ない）
  - 実機での効果：ライブラリ画面（実際に落ちた経路）は修正前GB級/数分の
    増加 → 完全にフラットに。プレイヤー画面（生の再生位置UIがあり一番
    厳しい）は毎分75〜97MB → 毎分12〜13MBまで低減。実測2点（1秒間隔で
    12.5MB/分・5秒間隔で4MB/分）を線形回帰すると、レンダー駆動の増加が
    約0.18MB/回、レンダーと無関係な残りが約2MB/分と見積もれる
    （測定点が2つしか無いため目安）
  - **残件**：プレイヤー画面はまだ完全にはフラットになっていない。上記の
    見積もりが正しければ、これ以上分割しても毎分2〜4MB程度が下限。ただし
    増加は「アプリが前面かつ画面が点いている間」だけで、バックグラウンド
    再生（画面消灯中含む）では起きない。警告閾値（3GB）に達するには画面を
    点けたままプレイヤー画面を3時間以上表示し続ける必要があり、通常の
    使い方では起きにくい。プレイヤー画面のさらなる分割（再生位置に依存する
    部分を独立した小さなコンポーネントへ切り出し、画面本体の再レンダー
    頻度自体を下げる）は、区間設定・キュー・シーク・リピートが絡む画面
    構造に手を入れることになるため、実際に長時間セッションで問題になった
    ときに着手する
  - 副次的な改善候補（未着手）：再生中でもアプリがバックグラウンドの
    ときはポーリング自体を止める（`AppState` を見る）。メモリへの効果は
    無い（バックグラウンドでは元々増えない）が、毎秒ネイティブ呼び出しを
    続けるのは電池の無駄なので、別の改善として価値がある
- **`getStatus()` は最大200ms古いキャッシュを返す──JS側の対処だけでは直せない**
  （2026-09-11、曲送り操作の反応が鈍く見えた不具合の調査で発覚）
  - 症状：次の曲ボタン等を押してから、曲名・ジャケット・ヘッダーのキュー位置が
    画面に反映されるまで最大1秒かかる。メモリリーク対策でポーリング間隔を
    250ms→1秒にして以降に目立つようになった
  - 紛らわしかった点：`onTrackChange` を受けて `setStatus(RetracksPlayer.getStatus())`
    を呼ぶ対処を JS 側だけに入れても、体感が変わらなかった。`getStatus()` が
    最大200ms古いスナップショットを返すため、直前の `status` と
    `statusEquals()` で同値と判定され、実質 no-op になっていた
  - 真因：`RetracksPlayerModule.kt` の `getStatus()` は保持している `snapshot`
    をそのまま返すだけで、呼ばれた時点でプレイヤーを読みに行かない。その
    `snapshot` の更新は200ms間隔のポーリング（`snapshotRunnable`）だけが
    担っており、状態が変わった瞬間（曲の切り替わり・リピート設定変更）に
    同期更新する経路が無かった
  - 対処：スナップショット計算を `refreshSnapshot()` として切り出し、
    `onMediaItemTransition`（曲が変わった瞬間）と `setRepeatMode()` の直後で
    同期的に呼ぶようにした（ネイティブの再ビルドが必要）。あわせて
    `getStatus()` の宣言（`RetracksPlayerModule.ts`）に「即時性は保証しない」
    旨のコメントを追加した
  - 同根の別バグ：`cycleRepeat()` も `RetracksPlayer.getStatus().repeatMode` を
    読んでから次の値を計算していたため、200ms以内にリピートボタンを連打すると
    2回目が古い `repeatMode` から計算され、同じ値に戻ってしまっていた
    （オフ→全曲→オフ→全曲…と巡回が進まない）。同じ `refreshSnapshot()` の
    追加で解消・実機確認済み
  - やらなかったこと：真因が分かる前に「ジャケット画像自体の読み込みが遅い
    のでは」という仮説でアルバムアートの先読み（`Image.prefetch`）を投機的に
    追加したが、真因（上記）を直したら体感が解消したため、効果未検証のまま
    リバートした（本アプリの他の性能改善は実測を伴うが、これだけは無かった
    ため）。「音はすぐ切り替わるのにジャケットだけ遅れる」を実際に観測した
    ときに、改めて実測とセットで検討する
  - 教訓：このモジュールで「JS側に対処を入れたのに体感が変わらない」ときは、
    まず `getStatus()` がネイティブ側のポーリング間隔ぶん古い値を返している
    可能性を疑う
- **リピートボタンだけ反応が遅く感じる──`cycleRepeat()` の「直後の読み直し」
  が機能していなかった**（2026-10、プレイヤー画面のリピートボタンの反応が
  鈍いという報告で発覚。上の項目の続き）
  - 症状：リピートボタンをタップしてもアイコンがすぐ変わらず、次の1秒
    ポーリングまで反映が遅れる。前後ボタンはイベント駆動（`onTrackChange`）
    のため遅延がない一方、リピートには対応するイベントが無く、
    `cycleRepeat()` 末尾の `setStatus(RetracksPlayer.getStatus())`
    （直後に読み直して即時反映しようとしていた行）に頼っていた
  - 主因と推定（計測なし）：`setRepeatMode()` は `onMain { ... }`（メイン
    スレッドへの非同期 post）の中で値を書き換える。Expo の同期 `Function` は
    JS スレッドで実行されるため（→ `RetracksPlayerModule.kt` 冒頭の
    コメント）、`setRepeatMode()` を呼んだ直後に同じ JS tick で
    `getStatus()` を呼んでも、post がまだ処理されておらず古い値を返す。
    つまり末尾の読み直しは呼ぶたびほぼ空振りしていたと考えられる
  - 対処：`onTrackChange` と同じ構成にした。Android は
    `Player.Listener.onRepeatModeChanged`（controller 接続後のみ発火）で
    `refreshSnapshot()` の後に `onRepeatModeChange` イベントを送る。iOS は
    `Player.Listener` が無いので `setRepeatMode()` 内で直接送る。
    `cycleRepeat()` の末尾の読み直しは削除し、JS 側は
    `addListener('onRepeatModeChange', ...)` で反映する（ネイティブの
    再ビルドが必要）
  - `setRepeatMode()` は `controller` ではなく `activePlayer()`
    （未接続中はサービス側のプレイヤーを直接書く）に書き込むようにしたため、
    起動直後の数秒間（controller 接続前）にタップしても設定自体は失われない。
    この間は `playerListener` が未登録で `onRepeatModeChanged` が呼ばれない
    ため、`setRepeatMode()` 側で直接 `onRepeatModeChange` を送っている
    （接続後にこの分岐を通ることはないので二重送信にはならない）
  - ウィジェット（`RetracksWidgetProvider`）がリピートを変えた場合も、
    controller 接続中であればこのイベントで即座に拾える。ウィジェットが
    書き込む `PlaybackService.playerOrNull()` は `MediaSession.Builder` に
    渡した Player そのもの（[PlaybackService.kt:179](../modules/retracks-player/android/src/main/java/expo/modules/retracksplayer/PlaybackService.kt#L179)）で、
    MediaSession は接続中の MediaController へ player の状態変化を自動転送
    する。曲の自然な終端での自動送り（`next()` を呼ばなくても
    `onMediaItemTransition` が飛ぶ）と同じ仕組みで、新たに検証したものでは
    ない
  - `cycleRepeat()` 冒頭の `RetracksPlayer.getStatus().repeatMode` 読み取り
    （連打対策、上の項目参照）はそのまま残した。`setRepeatMode()` 内の
    `refreshSnapshot()` もこの連打対策のために必要で、
    `onRepeatModeChanged` 側の `refreshSnapshot()` と役割が違うため重複では
    ない
  - 続き（同じ2026-10）：上のイベント化だけでは実機で「良くなったが、まだ
    微妙に遅い」という状態が残った。このリピート固有の残り遅延に限って言えば
    真因はネイティブではなく JS 側の再レンダー構造だった（`onRepeatModeChanged`
    は最初から `refreshSnapshot()` を呼んでいたため）。ただし後述の通り、
    再生/一時停止側では別にネイティブ側の更新漏れが残っていた。
    `player.tsx` はリピートアイコンを
    `usePlayback()` の value 経由（`repeatModeState`）で読んでいたが、
    `repeatModeState` は `status` が変わった「後」の別の `useEffect` でしか
    更新されないため、①イベントで `status` 更新→再レンダー、②その
    `useEffect` が `repeatModeState` を更新→再レンダー、という2回のレンダーを
    経てようやくアイコンが変わっていた。さらに ② の再レンダーは
    `usePlayback()` の value（大きな1つの Context）を作り直すため、同じ
    value を購読している `index` 画面（ライブラリ一覧、曲数が多いと重い）
    まで巻き込んで再レンダーしていた（`index` は `player` の下に
    Stack で積まれたままマウントされ続けている）。対処として
    `repeatMode`/`repeatModeState` を `usePlayback()` の value から完全に
    外し、`player.tsx` は（`progress` 表示などで元々 1秒ごとに再レンダーが
    発生している）`usePlaybackStatus()` の `status.repeatMode` を直接読む
    形にした。これで『イベント受信→1回の再レンダーでアイコンが変わる』
    形になり、`index` 画面を巻き込むこともなくなった
  - 教訓：ネイティブ側を直しても JS 側の Context 設計（大きな value を
    1箇所で作り直すと無関係な画面まで再レンダーされる）が別のボトルネックに
    なり得る。「イベント化したのに微妙に遅い」ときは、変更が実際にどの
    state・どの Context 経由で画面まで届いているかを追うこと
  - 上の再レンダー対処を実機に反映する前（Metro 再接続待ちの間）に、
    タップの手応え改善や楽観的更新（タップ直後にローカルで `next` を仮表示
    する）も検討したが、後者は解除条件とタイムアウトの両方が要るぶん複雑さが
    増す一方で効果は小さいと判断し見送った。実機で再レンダー対処を確認した
    ところ、体感は完全に解消し「めっちゃ早くなった」との評価を得た
    （2026-10、実機 Pixel 11）。見送った手応え改善（押している間だけ不透明度
    を下げる等）は、この画面の他のボタン（前後・再生/一時停止）にも無い
    見た目なので、入れるなら画面全体のボタンに揃えて別タスクで対応する
  - 同じ根本原因（ネイティブは `onPlaybackStateChange` イベントを送って
    いたが、JS 側 `playback.tsx` がリッスンしていなかった）で、再生/一時
    停止ボタンのアイコン反映も1秒ポーリング任せで遅れていた。同じ形で
    `addListener('onPlaybackStateChange', ...)` を追加して解消（実機で
    確認済み）
  - 上の対応を入れた直後、`onIsPlayingChanged()` だけ他の3つのリスナー
    （`onMediaItemTransition`・`onRepeatModeChanged`・iOS の
    `playbackChanged()`）と違って `refreshSnapshot()` を呼ばずに
    `sendEvent()` していたことが発覚（クロスレビューで指摘）。イベントで
    JS の `status.isPlaying` を更新した直後、1秒ポーリングが
    `SNAPSHOT_INTERVAL_MS`（200ms）ぶん古い native snapshot を取得すると
    `statusEquals()` が「違う」と判定し、一旦古い値へ表示が巻き戻ってから
    次のポーリングで再び正しい値に戻る、というちらつきが起こり得た
    （指摘時点では未計測。ポーリング周期1秒・ずれの窓200msから
    単純計算で2割程度の確率と推定）。他の3箇所と同じ順序
    （`refreshSnapshot()` → `sendEvent()`）に揃えて解消した
  - なお、再生中に次/前の曲ボタンを押すと一瞬だけ再生アイコンが出て
    一時停止アイコンに戻ることがある。これは曲の切り替え時に ExoPlayer が
    一瞬 `STATE_BUFFERING` を経由し、実際に音が進んでいるかを表す
    `isPlaying` が瞬間的に `false` を返すことによるもの（音切れは無い）。
    Media3 公式は独自UIでの再生/一時停止表示に `isPlaying` ではなく
    ユーザーの意図を表す `playWhenReady`（または `Util.shouldShowPlayButton()`
    相当）を使うことを推奨している。当初は実害が無いとして見送ったが、
    後日「直せるなら直したい」との要望で対応した（下記）
  - **`isPlaying` と `shouldShowPlayButton` を分離**（2026-10、クロスレビュー
    2件の指摘を踏まえて複数回修正）
    - Android：`Player.playbackState`・`playWhenReady`・
      `playbackSuppressionReason` から `shouldShowPlayButton()` を計算し、
      `snapshot`・`onPlaybackStateChange` の両方に乗せる。イベント送信は
      `onIsPlayingChanged`/`onPlaybackStateChanged` の2つを別々に実装すると、
      「バッファリング中に一時停止」のように `playWhenReady` だけが変わる
      操作でどちらも発火せず、最大1秒アイコンが誤ったまま残るケースが
      あった（クロスレビューで指摘・修正前は未検知）。`Player.Listener`
      の `onEvents(player, events)` で
      `EVENT_IS_PLAYING_CHANGED`/`EVENT_PLAYBACK_STATE_CHANGED`/
      `EVENT_PLAY_WHEN_READY_CHANGED`/`EVENT_PLAYBACK_SUPPRESSION_REASON_CHANGED`
      のいずれかを含むかで判定し、1回にまとめた（1操作で複数イベントが
      同時に変わる場合の二重送信も防げる）
    - iOS：当初 `player.timeControlStatus == .paused` で判定していたが、
      (1) `play()`/`pause()` 呼び出し直後に同期的に切り替わる保証がなく
      KVO も張っていないため最大1秒ずれた値が残り得る、(2) `player.rate`
      （元々の `isPlaying` の判定に使っている値）がそもそも「要求している
      再生速度」を表しており、バッファリング中も 1 のままである可能性が
      あり、だとすれば iOS はそもそも Android のような一瞬のアイコン変化が
      起きていなかった可能性がある、という2点をクロスレビューで指摘され、
      どちらも実機未検証だったため、安全側の `player.rate == 0` に変更した
      （play()/pause() の呼び出しと同期して確実に変わる値のため）。ただし
      `rate == 0` は常に `!isPlaying`（`rate > 0` の否定）と等価なので、
      iOS では Android のような「意図」と「実際の再生状態」の区別はできて
      いない。rate がバッファリング中も1のままなら（上の(2)の想定通りなら）
      ちらつきは起きないが、Android と同じく0へ落ちるなら、Android で
      直したのと同じちらつきが iOS には残る（2026-10時点で未検証）
    - `toggle()` をネイティブ関数として追加し、JS 側の
      `statusRef.current?.isPlaying` を見た分岐は撤廃（`statusRef` 自体も
      削除）。バッファリング中の誤判定や、イベントが JS に届く前の連打での
      重複送信を避けるため、現在の Player 状態を見て原子的に判定する
    - 未対応のまま残した点（既存の `play()`/`pause()` と同じ挙動なので
      劣化ではない）：Android の `toggle()` は、リピート OFF でキューを
      再生し終えた ENDED 状態で `shouldShowPlayButton` が true になっても
      `play()` を呼ぶだけで、`Util.handlePlayButtonAction()` のような
      `seekToDefaultPosition()` はしない。`toggle()` は `controller`
      （`activePlayer()` ではない）を使っており、接続前（起動直後の数秒）は
      `play()`/`pause()` と同じく何も起きない（`setRepeatMode()` は設定が
      消えないよう `activePlayer()` に書いているが、再生操作はそこまでする
      理由が無いため揃えていない）
- **iOSのローカルビルドがXcode 26.3で失敗する（`expo-modules-jsi`側のバグ、

### 13.6 再生位置の保存・復元を実機で確かめる手順（2026-10-15）

再生位置は再生中だけ5秒ごとに保存される（`src/playback.tsx`）。再生を続けたまま保存値を
記録すると、値が動き続けるので、再開した位置と比べられない。実際にこれで「既存の不具合では
ない」と誤判断しかけた（v2.48）。次の手順で測る。

1. 対象のキューを再生し、ある程度（10秒以上）進めてから**一時停止**する
2. 保存内容を読み出して、位置とカーソルを記録する。6秒ほど置いてもう一度読み、**同じ値**
   であることを確かめる（固定できていない状態で次へ進まない）
3. 別のキュー（小さいものと、1000曲級のものの両方を試す）を再生してから、対象のキューに戻る
4. 再開の数秒後の位置を、記録した値と比べる（再開位置＋経過時間になっているはず）
5. 直したコードと元のコードの両方で同じ手順を行う。タイミング依存の競合は、
   `console.log`にタイムスタンプを入れて、イベントと読み出しの順序で確かめるのが早い

端末内の保存内容は、debugビルドなら`adb exec-out run-as com.yskms.retracks cat databases/RKStorage`
（と`RKStorage-wal`・`RKStorage-shm`）で取り出し、`sqlite3`の`catalystLocalStorage`表で読める。
`retracks:position:v1:<キュー・キー>`が位置（ms）、`retracks:shuffle-cursor:v1:`・
`retracks:ordered-cursor:v1:`がカーソル。区間再生のときの位置は、区間の先頭を0とした値で、
プレイヤー画面の経過時間と同じ単位。


### 13.7 Metro無しで動く実機ビルドを、データを消さずにPixelへ入れる手順（2026-10-17）

外出先でテストするための手順。debugビルドは起動のたびにMacのMetroからJSを取るので、外出先では動かない。

1. `android/`で`assembleRelease`を、arm64のみ・**debug署名**で作る（JDK 17を指定し、`nice -n 10`を付ける）
   ```
   cd android && JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home \
     nice -n 10 ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a \
     -Pandroid.injected.signing.store.file=<絶対パス>/android/app/debug.keystore \
     -Pandroid.injected.signing.store.password=android \
     -Pandroid.injected.signing.key.alias=androiddebugkey \
     -Pandroid.injected.signing.key.password=android
   ```
   所要は、キャッシュが効いていれば1〜5分（初回は全アーキテクチャで約57分、13.5）。
   **`expo prebuild`は実行しない**（`android/`の中身が消え、`release.jks`・`keystore.properties`も失う。13.5）
2. 署名を**debug鍵**にする理由：端末のアプリが`expo run:android`で入れたdebug署名だと、`release.jks`で
   署名したビルドは署名が合わず、アンインストール（アプリのデータが消える）が必要になる。
   次の`expo run:android`も署名不一致で失敗する。debug鍵で署名すれば、データを残したまま上書きできる
3. 成果物の確認：`apksigner verify --print-certs`のSHA-256が`debug.keystore`と一致、`aapt2 dump badging`で
   `application-debuggable`が無く、`native-code`が`arm64-v8a`のみ。バンドル内に新しいコードの文字列があるか
   （`strings`）も見ると、古いJSを入れてしまう事故に気づける
4. インストールは`adb push`＋`adb shell pm install -r`（素の`adb install`は止まることがある）。
   **Pixelに「Play Protect：アプリを送信しますか」が出て、操作するまで`pm install`が止まる**。
   外部へアプリを送らない「送信しない」を選ぶ（`adb shell input tap`でも押せる）。macOSには`timeout`コマンドが無い
5. **releaseビルドは本番のAdMob広告ユニットを使う**（`__DEV__`でないため。`src/adConfig.ts`）。
   テストの端末でも広告を**タップしない**（誤タップはAdMobのポリシー違反）
6. これは配布用ではない（ストア提出用のAAB・IPAは別に作る。13.5）。使い終わったAPKは削除する

### 13.8 AndroidのR8（コード縮小・難読化・最適化）を有効にする（2026-10-18）

**背景**
- 1.2.0の公開後、Play Consoleの「DEXコードの最適化」が赤字になった（難読化率2%、最適化率・縮小率・R8の設定は`-`、
  DEX 66MB）。リリースビルドでR8を使っていなかった（テンプレートの`android.enableMinifyInReleaseBuilds`が既定の`false`）。
- Googleの公式ヘルプ（Play Console「technical quality requirements」）では、**2027年2月から、DEXが10MBを超える
  アプリは、アップロードごとに難読化・最適化・縮小の3つの率を各25%以上にする必要がある**（満たさないと
  Google Play上の表示と公開機能に影響しうる。ストアからの削除とは書かれていない）。それまでの赤字は推奨の表示。
- AGPは8.12.0（React Native 0.86.3が固定）。Playが`r8.json`を読む条件（8.10以上）を満たすので、Consoleの
  「AGP 9.0にアップグレード」は不要で、R8を有効にするだけでよい。

**実装**（`plugins/withAndroidR8.js`＋`plugins/android-r8-rules.pro`。`app.json`のpluginsに登録）
- `android.enableMinifyInReleaseBuilds=true`
- `proguard-android.txt`を`proguard-android-optimize.txt`へ置き換える（前者は`-dontoptimize`を含む）
- `android-r8-rules.pro`（Expoの注釈インターフェース`@interface expo.modules.**`のkeep。下の不具合の対策）を
  `android/app/`へコピーし、`proguardFiles`へ足す
- `android.enableShrinkResourcesInReleaseBuilds=false`を明示（**意図的に無効**。Playの要件はDEXの率だけで、
  リソース縮小は関係しない。JSから`require()`している画像4枚（`SplashFade.tsx`・`player.tsx`）は、リリースでは
  `res/drawable-*`に`assets_icrepeat.png`などの名前で入り、名前で探して読み込まれる。この名前はJSの側しか知らないので、
  リソース縮小に「未使用」と判断されて消える恐れがある）
- `org.gradle.jvmargs`を`-Xmx4096m`へ（minifyでAABに難読化の対応表（約170MB）が入り、テンプレートの2GBでは
  バンドル時に`Java heap space`で落ちた）
- **AGPを8.12.3（8.12系の最新パッチ）に指定**（`android/build.gradle`の`classpath('com.android.tools.build:gradle:8.12.3')`。
  今回の構成ではこの指定で、React Nativeが固定する8.12.0より新しい8.12.3が採用された。Gradleは通常、競合する版のうち新しい方を選ぶが、AABの`androidGradlePluginVersion`で確認する）。**外さない**。理由は下の
  「AGPを最新パッチにする理由」
- 置換対象・参照先が見つからなければ`prebuild`が失敗する。プロジェクトの複製（機密を除外してscratchpadへ作る）で、
  正常系と失敗系3種（置換対象なし・参照先なし・ルールファイルなし）を確認した

**実測**（r8.jsonから。試験ビルドはarm64のみ、最終AABは全アーキテクチャ。DEXのチェックサムは同一）

| | 1.2.0（R8なし） | R8あり・最適化あり（採用） | R8あり・`-dontoptimize` |
|---|---|---|---|
| DEX（非圧縮） | 66MB | 16.82MB | 25.2MB |
| 難読化率 | 2% | 84.34% | 約92% |
| 最適化率 | - | 84.02% | 無効（`noOptimizationPercentage`が`-26.98`で、意味のある値ではない） |
| 縮小率 | - | 84.39% | 約92% |

- 表の率は、`r8.json`の`noXPercentage`を「適用されなかった割合」と読み、100−Xとした値。**AGP 8.12.3（最新パッチ）の
  ビルドでは、Play Consoleの表示（3つとも84%）と一致した**（下の「AGPを最新パッチにする理由」）。一方、AGP 8.12.0では
  Consoleは難読化92%・最適化率と縮小率は`-`と表示した。公式ドキュメントでは、最新パッチ以外のAGPは`r8.json`の代わりに「`mapping.txt`か、DEXの推定から計算する」とあり、そのフォールバックで計算されたとみられるが、**算出方法は特定できていない**（versionCode 6の`mapping.txt`から数えた改名率は、クラス91.1%・メソッド73.8%・フィールド96.0%・合算77.9%で、92%とは一致しなかった）。最適化率・縮小率が`-`なのは、そのフォールバックでは難読化しか出せないためとみられる（未確認）。
  Consoleの吹き出しは、3つの率に共通で「最終DEXを分析した値で、R8の構成アナライザーと違いうる」とあるだけ
- `-dontoptimize`にすれば不具合は出ないが、最適化率が要件を満たすか分からないので採用しない

**最適化を有効にすると起きた不具合（重要）**
- 症状：起動直後に`RetracksPlayer.setSegment`が`ERR_UNEXPECTED`で拒否され、`FATAL EXCEPTION`でアプリが落ちる。
  リリースビルドだけで、`tsc`もdebugビルドも検出できない。`-dontoptimize`では起きない
- 原因：ExpoのRecord変換（`ReflectionRecordConversionStrategy`）は、各プロパティの`@Field`注釈を
  `descriptor.fieldAnnotation.key`で読む。`@Field`は注釈インターフェースで、プログラム内に実装クラスが無い
  （実体は実行時にAndroidのランタイムが動的Proxyとして作る）。最適化が有効だと、R8はこれを「実体の無い型のメソッド呼び出し」とみなして
  `throw null`に置き換える（R8後のバイトコードで確認。両戦略が1クラスに統合され、リフレクション側の分岐の
  ループ本体が`getClass(); throw null`になっていた）。自前モジュールの`TrackInput`・`SegmentInput`だけでなく、
  `expo-music-library`の`Record`も同じ経路。Expoのテンプレートは`-dontoptimize`なので、Expo標準の構成では出ない
- 対策：Expoの注釈インターフェースをkeep（`plugins/android-r8-rules.pro`の`-keep @interface expo.modules.** { *; }`）。
  最初は`@Field`・`@Required`の2つだけを残して直ったが、同じように注釈のメンバーを読む処理がもう1つあり
  （`ServicesRegistry`が`@ServiceInterface`の`clazz`を読む。`expo-constants`の`ConstantsService`が使う）、
  この呼び出しは最初の出荷物では`throw null`にならず残っていた（R8後のバイトコードで確認）が、**なぜ壊れないのかは
  確かめられていない**。運に任せないため、個別に列挙せずExpoの注釈インターフェース全体を残す形にした。
  追加で残るのは小さな注釈クラス6つ（`DoNotStrip`・`EitherType`・`DefinitionMarker`・`ServiceInterface`・
  `OptimizedRecord`・`OptimizedComposeProps`）だけで、率の変化は難読化−0.01ポイント、DEXは+0.02MB。
  `kotlin.reflect`や`kotlin.jvm.internal`を丸ごとkeepしても直らなかった（実験で否定）
- **Expo・React Native・ライブラリを更新したら、R8入りのリリースビルドを実機かエミュレータで起動・再生して
  確認する**。同種の問題はリリースの実行時にしか出ない

**調べ方**（再発したとき用）
- `adb logcat`の`FATAL EXCEPTION`・`has been rejected`・`NullPointerException`。難読化された名前は
  `~/Library/Android/sdk/cmdline-tools/latest/bin/retrace <mapping.txt> <stack.txt>`で戻す
- 原因を絞るには、`-dontoptimize`版との比較（A/B）、`dexdump -d`でR8後のメソッドを読む、自前モジュールに一時的な診断
  コードを入れてExpoの変換（`toAnyType<T>()`）を呼びスタックを出す、が有効だった。
  `ro.debuggable=0`（userビルド）のエミュレータではJDWP（`jdb`）は使えない。
  `node_modules`の書き換えは安全確認で拒否されるので使わない

**確認した範囲**（エミュレータ、API 36・arm64、最終構成のAPK。2026-10-18）：新規インストールと上書きの起動、
ライブラリ表示、再生とメドレー（`setSegment`）、通知（MediaSession・フォアグラウンドサービス）、
バックグラウンド再生、**Androidホーム画面ウィジェット**（追加、次へ・一時停止・再開）、

**AGPを最新パッチにする理由**（2026-10-20に確認）
- 公式ドキュメントでは、Playが`r8.json`から率を読むのは「AGP 8.10以降の**最新パッチ**」のとき。
  それ以外は、`mapping.txt`かDEXの推定になる。AGP 8.12.0（R8 8.12.14）は最新パッチではない
  （8.12系の最新は8.12.3で、R8 8.12.22を同梱。Google mavenで確認）
- 実験：AGP 8.12.3でビルドした実験用AAB（versionCode 7、arm64のみ）を内部テストに上げて、Consoleを見た。
  **最適化率84%・難読化率84%・縮小率84%、評価は高**。`r8.json`の値（84.02%・84.34%・84.39%）と一致した。
  つまり、AGP 8.12.0では、2027年2月の要件（3つとも25%以上）を満たしているかをPlayが判定できず、8.12.3に上げると
  判定できる。`noX`を「100−X」と読んだ推測も正しかった。R8 8.12.14と8.12.22で、`r8.json`の率の数値は同じ
- 対応：pluginが`classpath`のバージョンを指定する（`AGP_VERSION`）。AGPを変えると全タスクが再実行され、ビルドが長くなる
  （arm64のみで9分、全アーキテクチャで7分程度（キャッシュが温まった後））
- **React Native・Expoを更新してAGPが変わったとき、また8.12.4以降が出たときは、`AGP_VERSION`を見直し、Consoleで3つの
  率が出ることを確認する**（`https://dl.google.com/dl/android/maven2/com/android/tools/build/gradle/maven-metadata.xml`で版を確認）

**本番への昇格の条件**
- 本番へ昇格するのは**versionCode 8**（AGP 8.12.3。`build-output/retracks-1.2.0-vc8-r8-agp8123.aab`）。versionCode 6（AGP 8.12.0）は
  昇格しない（Consoleで率が`-`のため）。7は実験用で、昇格しない
- **versionCode 8は、内部テストで確認済み**（2026-10-20、利用者）：起動、再生、購入、購入の復元がOK。Play Consoleの`8.aab (1.2.0)`は、
  最適化率84%・難読化率84%・縮小率84%、評価「高」、非圧縮DEX 17.6MB、新規インストール21.5MB、ABIは4つ、権限15個
  （R8が8.12.14から8.12.22に変わったので、購入と復元を再確認した）
- 昇格するのは、内部テストに上げた同じAAB（再ビルドしない）。**昇格の操作は利用者が行う**（内部テスト→本番へのリリース）。
  versionCode 8はユーザーに見える変更が無い（R8とAGPだけ）ので、リリースノートは1.2.0のものを流用するか「内部の最適化」程度でよい
- **`versionName`**（`app.json`の`version`）は1.2.0のまま。versionCodeだけを上げる前例はv2.41（1.1.1のまま、3→4）。
  ただし`version`はiOSと共通で、1.2.1に上げるとiOS（1.2.0は審査中）との番号がずれる。本番へ出すまでに決める
- 設定を変えて再ビルドし、内部テストへ上げ直す場合は、同じversionCodeは再利用できないので、使用済みの最大（現時点で8）より
  大きい番号にする（`app.json`の`android.versionCode`。生成済み`android/app/build.gradle`にも手で合わせる）

**手順**（R8の設定を変えたとき・ビルドの検証）
1. 試験ビルドは`expo prebuild`を使わず、生成済み`android/`に手で反映して`./gradlew bundleRelease assembleRelease
   -PreactNativeArchitectures=arm64-v8a`（`nice -n 10`。署名は13.7のdebug鍵でもよい）。5分ほど。
   `r8.json`は`unzip -p <aab> BUNDLE-METADATA/com.android.tools/r8.json`
2. pluginの検証は、プロジェクトの複製で`expo prebuild --platform android --no-install`（`android/`・`ios/`・
   `docs/private/`・`build-output/`・`.claude/`・`.git`は除いてscratchpadへ。`node_modules`は`cp -cR`でほぼ無料）
3. 実際の`android/`に`expo prebuild`を使うときは13.5の手順（鍵2つの退避と配線の書き直し。署名のSHA-256を確認）
4. エミュレータでの確認：音声は`say`＋`afconvert -f m4af -d aac`で作り、`adb push`→`MEDIA_SCANNER_SCAN_FILE`。
   終わったら、自分のアプリをアンインストールし、音声を消し、自分で起動したエミュレータだけを止める
   （`adb shell rm`はスペースを含むファイル名が分割されるので、`'rm -f /sdcard/Music/RTest*'`のように全体を引用する）

**mapping.txt（難読化の対応表）の保管**
- AABにも入っていて、Play Consoleのクラッシュは自動で読み解かれる（Play Consoleヘルプ「Deobfuscate or symbolicate crash stack traces」による。AGP 4.1以降のAABなら、バンドル内の難読化解除ファイルをConsoleが自動で取り込み、アップロードは不要。APKの場合だけ手動のアップロードが要る）。手元でlogcatを読むときのために、リリースごとに
  `docs/private/mapping/<version>-vc<versionCode>/mapping.txt.gz`へ保管する（git管理外。171MBが12MBに圧縮される）。
  `android/app/build/outputs/mapping/release/mapping.txt`は`prebuild`や次のビルドで消える／変わる
- 1.2.0（versionCode 6）の分を保管済み

## 15. 要確認事項（未決定・曖昧な点）

2. ~~**開始位置＋再生時間が曲の長さを超える場合の挙動**~~ → **決定（2026-09-02）**
   曲の終端でフェードして次の曲へ。開始位置自体が曲より長い場合は0秒から再生。→ 4.2
3. ~~**自動スキップOFF時の挙動**~~ → **決定（2026-09-02）**
   自動スキップ＝RUSHモードのON/OFF。OFF時は区間再生を無効化し、曲を頭からフル再生する（A案）。→ 4.3
4. ~~**リピートの粒度**~~ → **決定（2026-09-02）／優先度：低**
   キュー全体のリピートのみ実装する。1曲リピートは「あってもなくてもよい」レベルのため対象外とし、必要になったら Phase 3 で検討する。

   全体設定を基本とし、曲ごとの個別設定を上書きとして持てる方針だったが、2026-09-11に個別設定は実装しないと決定。全体設定のみ。→ 4.2 / 4.3

   普通のプレイヤー準拠とする。一覧から曲をタップしたら**その一覧をキューとして再生開始**し、RUSH ON なら区間再生、OFF ならフル再生。割り込み再生という特別扱いは設けない（シャッフル順は 6.2 の永続化で保持されるため不要）。→ 10.4
7. ~~**キュー作成後の画面遷移**~~ → **決定（2026-09-02）**
